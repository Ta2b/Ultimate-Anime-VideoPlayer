# Rapport de l'audit 20. Socle commun (core)

Branche : `claude/project-thread-5j20iw`. Commit audité : `1e3d71fb9315cf7cc40807caaa19b60c63e1fd7f`. Date : `2026-11-09`.

## Verdict

Les briques vivantes du socle sont saines (threads qui n'échappent rien, boîtes bornées, écriture atomique avec fsync,
bibliothèques ouvertes par chemin absolu), mais l'écriture atomique ne survit pas à un antivirus sous Windows (QUA-07,
toujours présent), le nettoyage du journal laisse passer le nom d'utilisateur (WIN-08, démontré), un tiers environ des
lignes de la zone est du code mort, et la prémisse « `path::string()` lève sous Windows » est fausse pour le lecteur livré,
ce qui change la gravité de plusieurs défauts déjà fusionnés.

## Cadrage retenu

Pas de questions posées : Tatoub a demandé d'auditer au maximum sans cadrage. Retenu :

- cible NVIDIA sous TensorRT, Windows 11 et CachyOS. Le VRR est hors sujet : `display.h` (champ `vrr`) n'est pas creusé ;
- RIFE 4.25, RIFE 4.22 lite et DistilDRBA comptent autant. **Rien dans `core` ne ralentit DistilDRBA** : une boîte
  `Inbox` coûte un verrou et un réveil par message (quelques µs contre plusieurs ms de calcul par paire), le thread GPU
  est en rôle `Playback`, et l'attente CUDA est bloquante (`CU_CTX_SCHED_BLOCKING_SYNC`,
  `src/gpu/cuda/backend/tensorrt_backend.cpp:92`), donc MMCSS ne le rétrograde pas pour excès de CPU. En revanche, `core`
  prive de moyens de **mesurer** pourquoi DistilDRBA n'est pas plus rapide que RIFE : voir A20-11, avec la manipulation
  Nsight à faire sur la machine de Tatoub ;
- le fil tourne sans spdlog, toml++ ni Catch2 (`~/ajp-deps` absent) : les tests du dépôt n'ont pas été compilés. Deux
  défauts sont démontrés par de petits programmes compilés à part (copie exacte de `log_redact.cpp`, et `file_sync.cpp`
  lui-même) ; les tests qui échoueraient sont décrits.

## Windows contre CachyOS

- **Écriture atomique** (A20-01) : le renommage sur une destination ouverte réussit toujours sous Linux, et échoue sous
  Windows dès qu'un autre processus la tient sans partage de suppression.
- **Rôles des threads** (A20-06) : héritage par les threads de FFmpeg et baisse des E/S sous Linux seulement.
- **Pages de code** (A20-02) : le lecteur est en UTF-8 des deux côtés ; seuls les enfants Windows lisent leurs
  arguments dans la page ANSI.
- **Bibliothèques** (A20-07) : sous Linux, `dlopen` par chemin absolu ; les dépendances suivent le `RUNPATH` posé par
  `patchelf`, que `LD_LIBRARY_PATH` devance (renvoi 21).

## Points positifs

- `start_thread` tient ses deux promesses : rien ne lève au démarrage, rien ne sort du corps (`thread.h:78-101`), texte
  du refus compris.
- `Inbox` borne chaque type de message, garde une place au refus fatal, et réveille la boucle de la fenêtre hors du verrou.
- `write_atomic` écrit le temporaire sur le disque avant de le renommer, puis le dossier : une coupure ne laisse pas de
  fichier vide sous Linux.
- `DynamicLibrary` refuse tout chemin relatif et cherche les dépendances à côté de la bibliothèque.
- L'attente CUDA bloquante du backend TensorRT rend MMCSS sans danger pour le thread GPU sous Windows.
- `dir_entries` évite l'exception d'un `directory_iterator` qui échoue en cours de parcours.
